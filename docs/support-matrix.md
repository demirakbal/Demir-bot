## Additional-client adoption contract — item 044

Current working target is local Codex. No additional client implementation target was selected for this batch. Do not revive the removed duplicate cloud registration or claim that local installation creates a browser installation. The stable source/identity should be reused through a supported target-specific mechanism if a later client is selected; cloud synchronization stays deferred.

For a selected client, inspect its actual plugin/skill discovery format, filesystem visibility, tool exposure, context loading, native permission/approval semantics, private-profile support and supported update/uninstall mechanism. Separate portable procedure text from host adapters. A tool callable in Codex may not exist in browser ChatGPT; another host's hooks are not Codex enforcement. A shared display name does not prove a shared installation/source version.

Implement only the named missing adapter after establishing that client's contract and useful outcome. Carry the same scope/privacy/no-unrequested-test rules through supported instruction channels; where enforcement is weaker or a feature is absent, state that limit and keep the operation unavailable rather than silently bypassing it. Do not create a parallel coordinator, global config, duplicate account registration or a promise of all-harness compatibility.

Acceptance example: a later named client can discover the selected version, load only approved context, expose the required tool and enforce the operation's actual permissions; each claim needs that client's observation. Saving a compatible-looking file is source evidence only. No-action case: an ordinary local task uses Codex without setting up another client. Actual adapters/discovery/installation lifecycle remain pending client selection, supported access and applicable setup/run authority.
