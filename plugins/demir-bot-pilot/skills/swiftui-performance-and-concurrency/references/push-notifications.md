# App push notifications

Use for an explicitly requested app notification feature or supplied delivery failure. Establish the app/bundle target, environment, supported OS, current permission state, provider service and intended notification type. Keep local notification scheduling, visible remote notifications, background updates and ActivityKit pushes distinct. Reuse signing/provisioning, background-task and link-routing references only when the actual flow needs them.

Trace app → provider → APNs → app/display, naming the evidence available at each boundary. Apple's [registration guide](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns) distinguishes capability configuration, registration success/failure, current device token and forwarding to a provider. Obtain the current token through supported registration rather than assuming a cached token remains valid. Treat device tokens as sensitive routing data; bind registration to the correct user/device/app/environment, handle logout/account changes and invalid-token responses, and keep tokens out of logs, examples and skill files.

Use [permission guidance](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications) for a contextual request and a useful denied/changed-permission state. Permission to show notifications differs from registration, provider authentication and user's consent for the particular message. Do not repeatedly prompt, invent an entitlement or alter a developer account while writing guidance.

For the selected provider, inspect its real payload/header contract and environment, authentication/secret owner, expiry, duplicate/coalescing semantics and documented errors. [Apple's server overview](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server) separates provider submission from delivery; an accepted request does not prove display or user action. Keep the payload minimal; resolve protected content after authorization. Validate notification action/deep-link inputs, handle foreground/cold entry and prevent duplicate side effects. Reconcile an uncertain send before retrying.

Acceptance example: a selected app handles permission denial, token replacement, stale target data and notification entry without revealing another account's record. A delivery investigation reports the last observed boundary, rather than declaring APNs broken from one missing banner. No-action case: editing a settings label does not send a sample push. These are source-review conditions, not executed checks. No token registration, key creation, notification send, provisioning, build or device operation is performed by this roadmap update. Actual feature delivery needs the chosen app/provider and authorized access.

Official references reviewed 16 October 2026; recheck the selected SDK/provider contract for actual implementation.
