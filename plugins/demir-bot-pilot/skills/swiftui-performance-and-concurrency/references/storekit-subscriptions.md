# StoreKit subscription delivery

Use for a requested subscription feature or supplied entitlement failure in a named app. Establish deployment/SDK settings, actual product IDs/types and subscription groups, app-account ownership, existing purchase service and environment. Product configuration, contracts, pricing and store publication are separate account operations; do not invent products or modify commercial settings while preparing app source.

Trace product loading → purchase outcome → transaction verification → entitlement decision → durable delivery → transaction completion. Keep loading/unavailable, user cancellation, pending approval, verified/unverified, expired and revoked states distinct. A tapped purchase button or returned transaction identifier alone does not prove entitlement. Never grant new access solely from an unverified payload; define an appropriate recoverable state without accidentally discarding previously established valid access.

Use target-compatible [current entitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements) and transaction updates for their documented roles. Current entitlements are not all transaction history and omit refunded/revoked products and consumables. Derive access from the product's actual semantics; non-renewing subscriptions need their own validity logic. Avoid granting duplicate content when launch reconciliation, purchase and update streams describe the same transaction. Give the long-lived listener one owner and apply the parent's cancellation/isolation rules.

Apple's [Transaction contract](https://developer.apple.com/documentation/storekit/transaction) associates finishing with delivered content/service. Commit the actual entitlement/delivery before finishing, with recovery if interrupted. If a backend is authoritative, inspect its real signed-data validation, environment, account binding, idempotency and outage contract; client UI state is not server authorization. Do not add a receipt server solely because the capability is listed here.

Define restore/reconciliation UX, renewal/grace/billing-retry/expiry behavior appropriate to the product, offline limits and account switching. Distinguish App Store account from the app account and preserve privacy. Acceptance example: a selected subscription handles pending purchase, duplicate update, revocation and relaunch without inventing access or reporting cancellation as failure. These are proposed conditions; sandbox/purchase checks remain unrun. No-action case: an unrelated view change does not add a paywall or purchase listener. No purchase, sandbox login, product creation, build or store action follows from this guidance update.

Official references reviewed 16 October 2026. Actual implementation requires the app/product contract and selected client/server ownership.
