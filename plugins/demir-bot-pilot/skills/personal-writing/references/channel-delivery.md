# Additional channel drafting and delivery boundary

Use for an explicitly requested channel beyond the existing email/LinkedIn procedures, or a requested cross-platform adaptation. Resolve the actual channel/account, reader, format and source. Reuse content-repurposing for source fidelity. Do not install a provider or create a tone specialist merely because a platform is listed.

## Channel ownership

Email uses the private email-tone owner and resolved recipients. LinkedIn uses linkedin-tone, demir-linkedin and its existing actions contract. For X or another selected social channel, use the requested style and format without claiming a previously calibrated voice. A future durable channel calibration requires approved examples and persistence scope at its own private owner; shared facts remain canonical. Do not copy private email examples or channel-specific hooks into all platforms.

For each requested adaptation, name the exact final text, media/alt text, links, audience/visibility, account and timing. Preserve attribution, team credit, actual implementation state and important qualifications in each independently usable post. Check current official format/length/media/link constraints only for the selected provider/version; do not hard-code a universal limit, assume feature parity or silently truncate a claim. If the requested output cannot fit honestly, narrow it or identify the missing decision.

## Typed provider operation

Before an authenticated implementation, inspect the available tool/API and existing account connection. Record an operation contract: provider and target identity, read/write type, payload schema, credentials/permission boundary, idempotency/retry behavior, expected result and failure/uncertain outcome. An access/read success does not establish publishing permission. Prefer an already supported provider over a second publisher; do not invent an X API schema or claim that a Buffer connection supports every platform.

Drafting or approval for one channel/account does not authorize another. Final-action approval binds content, account, recipients/audience, assets and schedule. Material changes need the applicable renewed decision; reuse valid exact authority without repeating approval unnecessarily. Provider result must confirm the actual action; queued/attempted/timeout is not published. Retain only minimal safe receipt evidence and reconcile uncertain results before an authorized retry to avoid duplicates. Do not fall back to another account/channel after denial.

Return the requested drafts and actual status: draft, needs source confirmation, awaiting action authority, blocked by provider/access, queued, confirmed published or uncertain. No bulk engagement, scraping, unrequested auto-posting, cross-account permission transfer or background campaign. Scheduling, paid media and analytics each retain their own scope.

Expected example, not a run: an approved project summary becomes an X draft and a LinkedIn draft, each preserving the same factual status; neither is posted, and the X copy uses the requested style rather than claiming LinkedIn tone calibration. No-action case: asking for one LinkedIn post does not generate five-channel variants. Reusable procedure is saved; an executable publishing adapter requires the selected provider/account and its actual operation schema.
