# Selectable preference interactions


For A/B calibration and other bounded preference questions, present selectable choices through a currently supported question tool, obeying its mode restrictions. Tool acceptance does not prove the user can see buttons. If the user reports that choices are not clickable, do not repeat the same invisible interface or require typed A/B answers: put native Codex follow-up actions in the final response, one per option, when the client supports them. Use the documented `- :codex-followup[Label]{prompt="Self-contained selected answer and question context"}` syntax. Keep each prompt specific to the current round and include a custom-answer invitation. These actions submit or prepare a user reply; do not claim an answer arrived until it does. If neither interface is supported, explain that client limitation and use concise text choices. Skill instructions cannot repair the host UI or guarantee rendering. Never use preference choices as implicit authorization to publish, send or perform unrelated actions. In adaptive exercises ask one round at a time and preserve previous answers.

When a bounded preference question is warranted, actually present it through the currently permitted selectable interface; merely saying that buttons could be used or listing choices in prose does not fulfill this preference. Use the tool available in the active mode (including an asynchronous question tool where appropriate); if unavailable, emit supported native follow-up choices. Keep free-text needs such as a project path separate from selectable preferences. Never claim UI rendering was verified from a tool call or text simulation alone. This rule does not add questions to otherwise clear tasks.

When the question tool supplies built-in free-text/custom input, include only substantive choices in its options array. Do not add “Other”, “Custom answer”, “I will specify it”, or an equivalent placeholder option. For native follow-up actions without built-in custom input, invite a typed alternative in surrounding prose rather than adding a fake choice. Follow the current tool schema; do not infer that a user clicked a button merely from receiving an answer.
