## Missing-provider and access fallback

For the requested operation, distinguish installed package, currently exposed capability, authenticated access and operation-specific evidence using capability-maintenance.md. A catalogue mention or successful account read does not establish a write operation. Discover only relevant available tools before declaring a capability missing; do not install, authenticate or make live probe calls solely to complete a route decision.

If the preferred provider is unavailable, first use supplied content or an existing authorized local/built-in/connected capability that can meet the requirement with equivalent evidence quality and privacy boundaries. Follow required source rules, such as official documentation, and explicit provider choices. If the user specifically requires that provider, a fallback can support independent work but does not count as fulfillment of the provider-specific operation; disclose the limitation. Never ask for redundant tagging when the needed capability is already available.

Distinguish an unavailable tool from an authentication failure, a missing project/file and an explicit permission denial. Report the actual dependency and finish unaffected work. An alternative provider must not bypass a denial, widen data access or send private material to a new destination without applicable authorization. If no suitable fallback exists, state the blocked operation rather than fabricating results, endpoints, credentials or connection evidence. Do not install a new specialist or provider to disguise a missing runtime dependency.

Return only the material fallback choice, supported result and limitation in ordinary task feedback. Do not create a capabilities report, routing record or repeated discovery loop unless requested. This is on-demand guidance, not automatic failover infrastructure or verified provider access.
