## Native execution environment selection

Choose the smallest currently available execution surface that can produce the requested result. Keep the user's explicit environment/model selection. These preferences are instructions, not an automatic switcher or entitlement matrix. Account plans, workspace controls, rollout and host tools determine actual availability; inspect only the required capability when the task depends on it.

| Task/trigger | Preferred available surface | Access boundary and fallback |
| --- | --- | --- |
| Supplied email/post draft or simple explanation | Current chat plus relevant writing/source procedure | No connector is needed unless necessary evidence is missing; deliver a draft/answer without sending or changing mode. |
| Substantial document edit, file analysis or interactive artifact | Work/current artifact tools when available | Use the actual accessible file/Page; a local path does not grant cloud access. Otherwise work from supplied content and name the missing file/tool. |
| Repository or SwiftUI implementation | Current authorized local Codex checkout | Read AGENTS.md and scoped source. A different thread/host needs an explicitly authorized handoff and the relevant execution contract. No silent code copy to cloud. |
| Service lookup/write | Relevant already-available plugin or API | Installation, exposure, authentication and operation-specific evidence are separate. Reads do not establish writes; preserve action/content/destination approval. |
| Reusable project sources and decisions | Project context plus selected Space/Pages sources when relevant | Follow profile-loading/context ownership; retrieve the source rather than assume universal visibility. No automatic Page creation or migration. |
| Explicit recurring check or scheduled follow-up | Host scheduling/automation capability | Resolve scope, cadence, destination and notification intent; ordinary implementation does not schedule itself. |
| Deliberately assigned ongoing responsibility | An available dot, using supported Work/Codex handoffs | Confirm account eligibility and actual local-computer connection when local skills/files are needed. If unavailable, an authorized Codex chain can implement the same source scope in its active turn; it is not an always-on replacement. |

Before a switch/dispatch, inspect whether the current session actually exposes the operation. A recommendation is not an executed switch. If unsupported, continue useful work here or provide the bounded handoff at a true transfer boundary; do not claim a task was created. Local Codex configuration does not automatically configure managed Work or a cloud dot. Carry only relevant constraints through supported channels.

Use the user's configured model unless they request a change or applicable instructions authorize one. GPT-6.1 Sol is one documented option where available; do not force it into every host, assume pricing/entitlement, substitute a model in a fixed comparison or buy API capacity to match a roadmap. A plugin catalogue does not authenticate services or enforce the policy.

Platform references reviewed for these boundaries: [developer settings](https://learn.chatgpt.com/docs/developer-settings), [models](https://learn.chatgpt.com/docs/models), [dot computers/apps](https://learn.chatgpt.com/docs/dots/computers-and-apps). Recheck affected facts when a task depends on current availability. No mode-switch, provider-write or background-runtime operation was verified by saving this table.

For an explicitly requested on-demand local status view, use [status-dashboard.md](status-dashboard.md). The bundled read-only renderer accepts only selected package metadata and approved evidence summaries; do not activate it during ordinary tasks or treat displayed approvals as authority.

For requested notifications, use [notification-delivery.md](notification-delivery.md) for minimal payloads, actual destination/approval and explicit deduplication/outcome state. Existing conversation progress does not require a new provider; no watcher or sending action is implied.

## Missing-provider and access fallback

For the requested operation, distinguish installed package, currently exposed capability, authenticated access and operation-specific evidence using capability-maintenance.md. A catalogue mention or successful account read does not establish a write operation. Discover only relevant available tools before declaring a capability missing; do not install, authenticate or make live probe calls solely to complete a route decision.

If the preferred provider is unavailable, first use supplied content or an existing authorized local/built-in/connected capability that can meet the requirement with equivalent evidence quality and privacy boundaries. Follow required source rules, such as official documentation, and explicit provider choices. If the user specifically requires that provider, a fallback can support independent work but does not count as fulfillment of the provider-specific operation; disclose the limitation. Never ask for redundant tagging when the needed capability is already available.

Distinguish an unavailable tool from an authentication failure, a missing project/file and an explicit permission denial. Report the actual dependency and finish unaffected work. An alternative provider must not bypass a denial, widen data access or send private material to a new destination without applicable authorization. If no suitable fallback exists, state the blocked operation rather than fabricating results, endpoints, credentials or connection evidence. Do not install a new specialist or provider to disguise a missing runtime dependency.

Return only the material fallback choice, supported result and limitation in ordinary task feedback. Do not create a capabilities report, routing record or repeated discovery loop unless requested. This is on-demand guidance, not automatic failover infrastructure or verified provider access.

For a requested workspace, mail, calendar or messaging integration, use [workspace connectors](workspace-connectors.md) to resolve the actual useful gap and target before reusing a provider or implementing a narrow adapter.
