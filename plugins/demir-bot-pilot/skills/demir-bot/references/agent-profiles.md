# Optional execution profiles

The Demir Bot development checkout defines four project-scoped native Codex profiles under `.codex/agents/`: `demir_coding`, `demir_research`, `demir_university` and `demir_career`. Each standalone TOML uses the documented `name`, `description` and `developer_instructions` fields. No model/effort, MCP, sandbox or approval override is set; parent configuration applies. Skill `agents/openai.yaml` files remain invocation metadata, not these execution profiles.

| Role | Select for an explicitly authorized bounded assignment | Relevant existing procedures |
| --- | --- | --- |
| demir_coding | Owned repository change or fix | Actual repository guidance; relevant architecture/SwiftUI/refactoring/Git owners only |
| demir_research | Independent substantial research/source review | deep-research-and-idea-validation and its relevant academic/source references |
| demir_university | Selected assignment stage, guided explanation or final requirement review | Existing three assignment skills according to the assigned mode |
| demir_career | Email/application/LinkedIn drafting or opportunity preparation | personal-writing, channel tone and demir-linkedin as relevant |

The canonical execution policy is [execution-scope.md](execution-scope.md). Profiles point to that owner rather than store personal facts, tone or another policy database. Pass an exact task, allowed files/actions, existing human authority, relevant sources, acceptance and return/stop conditions using the existing compact handoff. Give workers minimum relevant context; the parent owns shared integration and per-item reporting. Profiles cannot self-spawn or create an ongoing responsibility.

These are saved source definitions, not launched agents. This package does not globally install the checkout's `.codex/agents/` files into every repository or register them with Work, a dot or the Agents API. Native discovery depends on the actual supported client and active project. Confirm the current host contract before requested use; if native custom profiles are unavailable, apply the relevant procedure inline in the current assistant and report that no separate agent ran. Do not copy the profiles to a home directory, enable features, change account access or create a custom orchestrator just to satisfy their presence.

## Admission and transfer procedure

For an authorized coordination assignment, apply [item 062's bounded native coordination contract](execution-scope.md#bounded-native-coordination--item-062) before dispatch. It owns writer reservations, dependency order, finite work and revision limits, lifecycle transitions, cancellation and item 065's verification recommendation. Keep these mechanics in the shared policy rather than duplicating them in each native role. All four existing profiles already require that policy; authoring it does not authorize using them.

1. Resolve the requested outcome in the current assistant. Keep a simple draft, short explanation, tightly coupled change or task with unresolved controlling requirements inline.
2. Establish actual human delegation/task-dispatch authority and the host's tool contract. Having role files or an eligible independent task is insufficient. User-visible Codex tasks, subagents and a dot responsibility are different operations; authorize the actual one.
3. Name the independent deliverable, minimum sources, fixed owned files if editing, acceptance and return boundary. Use context-efficiency's existing seven-field handoff, with execution-scope's relevant contract under Constraints. Do not pass full private profiles or unneeded conversations.
4. Select an exposed role only where the current host supports it. Inherit the chosen parent model/settings; explicitly requested overrides must also fit the host contract. A desktop profile does not register an API agent or Work/dot agent. If unavailable, do the procedure inline without claiming a worker ran.
5. Review the returned artifact/findings against the source and assignment, integrate once and preserve concurrent edits. Reject scope expansion, invented proof and unrequested tests/external actions. A worker's reply does not authorize messaging another chat. The parent reports known worker plus integration/coordination effort; no assumed savings.
6. For failure, interruption or ambiguous tool outcome, inspect the supported task status once as needed, preserve unfinished work and choose a contained next action. Do not retry identical failures, spawn replacements indefinitely or bypass a denial. Cancellation of the parent is not proof all host tasks stopped; use supported per-task controls only within authority and report unknown states.

## Host-specific handoff boundaries

| Host path | Handoff content and dependency | What completion establishes |
| --- | --- | --- |
| Current local Codex task | Actual checkout/AGENTS.md and relevant source; current parent policy/authority. Apply the role procedure inline if worker use is not requested. | Saved source and inspected changes only; no separate agent or background continuation implied. |
| Explicitly authorized native Codex worker | Named role or equivalent supported worker, independent deliverable/ownership, minimum sources and shared scope contract. Parent retains integration. | A returned result when observed; native discovery, stop/cancel and effectiveness are otherwise unverified. |
| Explicitly authorized local Work/Codex task from a dot | Real computer connection and accessible checkout; current roadmap revision/selected items; no-tests/no-cloud-sync constraints; agreed update cadence and stopping condition. | Actual task creation/updates only after the host confirms them; a prepared handoff alone creates nothing. |
| Cloud Work/dot without local access | Only sources already accessible within approved data boundaries; no private-profile upload or invented local path. | Independent cloud deliverables in scope, or a precise missing connection; it does not update local source automatically. |

For a future dot assignment, resolve its current account availability and connection, then instantiate the canonical roadmap's assignment template with the actual checkout, selected items and permissions. Give per-item timed updates in the existing conversation and continue eligible work only under that assignment. If dots are unavailable, an authorized active Codex chain uses the same source requirements and notifications; do not install a substitute autonomous runtime or claim it will work while the session is stopped.

No team, dispatch, new chat, comparison, model evaluation, background schedule or dot setup is performed by authoring this procedure. Reuse existing native mechanisms rather than adding an agent manager service.
