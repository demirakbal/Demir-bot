For roadmap item 075, see [behavioral cases and bounded protocol](../behavioral/README.md). Retain the stable B086 case identifiers despite roadmap renumbering. Use the applicable retained evidence and current user-approved scope for acceptance status; the suite's historical preparation notes are not current run results. Loading these assets does not authorize model runs or real actions. Keep reviewer expectations separate from subject inputs.

Use only when Demir explicitly requests planning, writing or running an assistant evaluation; these are separate scopes. Installation of this reference authorizes none of those runs.

Select representative cases from the actual question: a clear code change, materially ambiguous request, requested existing-test run, research with conflicting sources, exact approved publication versus a changed draft, missing account access, privacy-sensitive input, and a deferred roadmap item. Use synthetic data and mocked external actions by default; no real messages/posts/deployments. Record expected boundaries from user requirements before observing outcomes, not by copying skill wording.

Assess task completion, correct specialist/provider routing, unnecessary questions, missed requirements, unauthorized tests/docs/actions, truthful evidence status and appropriate next steps. Record concrete errors and coverage rather than an invented overall quality score. If comparing versions, keep cases, tools and task conditions comparable; distinguish random variation, actual token/latency measurements and estimates. Include setup, retrieval, retries and review effort. No promised savings or extra subscription allowance.

Use a small meaningful set, stop at the authorized scope and report failures honestly. No automatic fix/retest loop, live-account checks or reports/files unless requested. This is a Demir-specific synthesis of the approved optional roadmap proposal, not an imported evaluation framework.

## Item 076 — Bounded before/after comparisons

This is comparison guidance, not a runner or permission to execute. Reuse the [measurement contract](../../context-efficiency/references/runtime-options.md#measurement) for baseline/candidate records, metrics, full overhead and attribution limits, and [bounded improvement](../../demir-bot/references/capability-maintenance.md#bounded-feedback-driven-improvement) for diagnosis, source changes, persistence and recovery. Do not duplicate those records or create a new suite.

### Establish whether a comparison is warranted

Name a concrete proposed instruction change: affected owner/passage, exact before/after wording or diff, observed mismatch (or explicitly hypothetical improvement), intended outcome and plausible regression. A satisfactory answer alone does not show that a skill caused it. If no supported change warrants comparison, record `No comparison candidate selected; effectiveness not measured` in the authorized task record or conversation and stop. Do not invent a defect, modify a working rule to obtain a candidate, or reopen an accepted evaluation scope.

### Freeze the comparison before collecting responses

- Select the smallest relevant subset of [existing independent cases](../behavioral/cases.md): the target behavior plus adjacent behavior that the change could damage. Preserve case/oracle versions and document any necessary adaptation; writing new cases requires applicable authorization. Define observable success, forbidden behavior and material trade-offs from the task requirements before seeing either condition's responses. Keep these reviewer criteria out of subject inputs and apply them equally to both versions.
- Identify the actual baseline and candidate content, including uncommitted changes and supplied excerpts. Record installed identity separately. Keep the model/settings, task inputs, available tools, enabled plugins, profile conditions and invocation method comparable. A tagged installed-plugin run and a supplied-excerpt run are different conditions; switching plugins or environments is not evidence that an instruction edit helped. Disclose unavoidable differences and restrict causal claims accordingly.
- State the case IDs, samples per condition, order, total attempt limit, authorized usage/time limits and stop rules before execution. Honor a user-selected single sample and no-retry limit; it provides no estimate of repeatability. Additional conditions or samples require explicit scope. Do not silently reuse a previous campaign's allowance. For separately authorized repeated sampling, use fresh contexts and a predetermined balanced order where feasible.
- Require a suitable boundary for each action case. Use synthetic data and mock-only actions; when only text is available, assess described decisions and mark execution/persistence unassessed. Skill loading, correct application and operational enforcement are separate observations. Unknown command contents are unknown, not evidence of either compliance or violation. Stop on attempted real actions, private-data exposure or loss of the agreed boundary; preserve the consumed attempt without replacement unless explicitly authorized.

### Assess outcomes without manufacturing improvement

Pair baseline and candidate results by case and condition. Retain original authorized evidence locators and criterion-level excerpts/traces; record met, violated or inconclusive, with not-run and setup failures distinguished. Include all consumed attempts, not only successful or inexpensive ones. Keep records and private material outside the distributable plugin; use conversational records when file retention is not authorized.

Report target gains, adjacent regressions, unchanged outcomes and missing evidence separately. Claim an observed improvement only for comparable evidence showing the intended gain with the predeclared required criteria preserved; mixed outcomes remain a trade-off, not an unconditional success. Missing or incomparable evidence is inconclusive. Model self-ratings and user acceptance of one version are not a before/after comparison. Do not promote or persist a proposed lesson merely because a comparison looks favorable.

Use the measurement contract for available usage and full setup, retrieval, review, failure and coordination overhead. Missing task attribution prevents whole-task savings claims; subscription percentages and shorter replies are not cost measurements. A single pair supports only a case-specific observation, not general reliability or effectiveness.

Report guidance saved, candidate selected or absent, execution authorized/not authorized, comparison observed/not run, and effectiveness supported/unverified as separate states. Finish the authorized source work without launching a fix/evaluate loop, adding a baseline condition, refreshing caches/indexes or starting the next roadmap item.
